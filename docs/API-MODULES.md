# 接 API：邊個功能用咩模組，點樣慳得同時做得好

> 呢份文件答一條問題：**工作台要真正跑起身，每個功能應該接咩，點樣唔好燒錢。**
> 路由表本身係可執行嘅設定 —— `workbench/models.py`。呢度講點解。

---

## 先講一句最重要嘅

**呢個工作台最大嘅成本，唔係生成內容，係每次生成之前要讀嘅嘢。**

每寫一篇稿，模型都要讀：品牌憲法、語氣檔、已批准證據、平台規格、受眾語言。
呢堆嘢加埋通常 8,000–15,000 token，而且**每次都一模一樣**。

一個客一星期出 12 篇（4 平台 × 3 條），每篇經研究、文案、改寫、QA 四步，
即係一星期讀呢堆嘢 48 次。唔處理嘅話，你 80% 嘅帳單係喺度重複讀同一份檔案。

所以下面第一項唔係「揀平啲嘅模型」，係 **prompt caching**。

---

## 一、Prompt Caching —— 慳最多，而且完全唔犧牲質素

品牌知識庫每次都一樣 → 做成 cached prefix。快取命中嘅部分大約係原價一成。

```python
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    system=[
        # 呢嚿唔會變 —— 放最前，做快取斷點
        {"type": "text", "text": brand_bible + voice_profile + approved_claims,
         "cache_control": {"type": "ephemeral", "ttl": "1h"}},
    ],
    messages=[{"role": "user", "content": todays_brief}],  # 每次唔同，放最後
)
```

**要留意嘅陷阱** —— 快取係前綴比對，前面改一個 byte，後面全部作廢：

| 會靜靜雞令快取失效嘅嘢 | 點解 |
|---|---|
| 在 system prompt 入面放 `datetime.now()` | 每次都唔同 → 每次都 miss |
| 用未排序嘅 `json.dumps()` 塞設定 | key 次序會變 |
| 每個客用唔同次序砌 brand brain | 順序要固定 |
| 中途改 `effort` | 會令 messages 快取作廢 |

驗證方法只有一個：睇 `response.usage.cache_read_input_tokens`。
**重複幾次之後佢仲係 0，即係你根本冇快取到**，唔好靠感覺。

> 工作台入面已經幫你做好一半：`brand/brain/` 嘅檔案次序係固定嘅（01–08），
> 而且 BIBLE 唔會每次重生。淨低要做嘅係砌 prompt 嗰陣次序固定。

---

## 二、Batch API —— 慢一半時間，平一半錢

**呢個工作台天生啱用 Batch，因為佢本身就唔係即時系統。**

睇返設計：所有內容都係入 `queue/` 等人審，冇一篇係即刻出街。
既然人要隔幾個鐘先審，模型早四小時定遲四小時交，完全冇分別。

```python
batch = client.messages.batches.create(requests=[
    {"custom_id": f"{client_slug}-{platform}-{n}",
     "params": {"model": "claude-sonnet-5", "max_tokens": 4000, "messages": [...]}}
    for ... in weekly_jobs
])
# 之後 poll .processing_status 到 "ended"，再 stream results
# 結果次序係亂嘅 —— 一定要用 custom_id 對返，唔好用位置
```

**啱用 Batch**：選題、寫稿、平台改寫、週報 —— 即係每週排程嘅嘢，佔工作量九成。
**唔啱用**：留言分流同回覆草稿（客人等緊）、QA（塞住成條線）。

## 三、模型分層 —— 按「工作性質」分，唔係按「重唔重要」分

| 崗位 | 模型 | Effort | Batch | 快取 |
|---|---|---|---|---|
| 爬取／抽取 | `claude-haiku-4-5` | low | ✓ | — |
| 語氣蒸餾 | **唔用模型**（`distill.py` 直接算） | — | — | — |
| 研究／選題 | `claude-opus-5` | high | ✓ | ✓ |
| 文案（Master） | `claude-opus-5` | high | ✓ | ✓ |
| 平台改寫 | `claude-sonnet-5` | medium | ✓ | ✓ |
| QA／紅線檢查 | `claude-opus-5` | high | — | ✓ |
| 留言／私訊分流 | `claude-haiku-4-5` | low | — | ✓ |
| 回覆草稿 | `claude-sonnet-5` | medium | — | ✓ |
| 週報／覆盤 | `claude-opus-5` | high | ✓ | ✓ |

第一方 API 價（每 1M token，2026-06 快照 —— 會變，落單前核返）：
`claude-opus-5` $5 / $25 · `claude-sonnet-5` $2 / $10 · `claude-haiku-4-5` $1 / $5

**分層嘅邏輯**：

- **爬取**係 token 量最大嘅一步（成個網頁掉入去），但完全唔需要判斷 → Haiku。
  呢一步慳到嘅錢，比其他所有步加埋都多。
- **平台改寫**係量最大嘅重複工作（4 平台 × 12 篇 × N 個客），
  而且 Master 已經定咗觀點同證據，改寫係**受約束**嘅工作 → Sonnet。
- **研究、文案、QA** 係開放性判斷，冇標準答案 → Opus。

### 呢兩個位唔准為成本降級

**QA。** 佢睇落似「對住清單逐條檢查」，實際要判斷「呢句算唔算功效宣稱」。
呢個係最後一道攔截。攔唔到就出街，出街咗嘅嘢收唔返。
一次違規嘅代價，遠遠大過成年 QA 嘅模型費用差額。

**語氣蒸餾根本唔好用模型。** 唔係因為貴，係因為模型睇完 40 條帖會寫
「語氣親切專業」呢類唔可驗證嘅描述。統計數字先逼到你寫
「平均 38 字一句，感嘆號 50 條入面出現 3 次」—— 呢類描述先至令兩個唔同嘅寫手寫出似嘅嘢。
`scripts/distill.py` 直接數，成本零。

### 先試呢個，先好砌多模型級聯

降 effort 通常已經夠。`claude-opus-5` 行 `effort: "medium"`，
好多時已經好過舊一代模型行 `high`，而且**只用一個模型 = 只有一個快取命名空間**。
級聯多個模型會令快取分散（快取係綁模型嘅），慳嘅隨時抵唔返蝕嘅。

順序：**先做快取 → 再開 Batch → 再調 effort → 最後先考慮換模型。**

## 四、生圖 —— 呢度嘅成本控制係「唔好重生」

**一定要用圖像模型，唔可以用 code 砌版。**
用 CSS／canvas 排出嚟嘅圖，每個元素數學上啱位，但一睇就知係機器砌 —— 生硬。

但圖像模型有個硬限制：**出唔到準確文字**。所以每個 style pack 要聲明：

| render_mode | 幾時用 | 點做 |
|---|---|---|
| `image-only` | 純視覺、冇字，或者字錯咗都唔緊要 | 直接生 |
| `image-plus-text-layer` | **有免責聲明、價格、資格、數據嘅一律用呢個** | 圖像模型生底圖，文字用圖層疊上去 |

健康類、功效類客戶（紮肚、美容、兒童產品）**永遠**行 `image-plus-text-layer`。
免責聲明燒錯一個字，等於冇聲明。

**生圖成本控制，重點唔係揀邊個模型，係減少重生次數。** 重生嘅三大原因：

1. **冇寫「從來冇出現」欄** → 模型自己加漸變、金色點綴、bokeh → 唔似品牌 → 重生。
   呢欄係 `style/brand-visual.md` 入面最重要嗰欄。
2. **一次生一張** → 應該一次生 4 個變體，人揀一張，唔中意先重生。
3. **文字燒入圖** → 錯一個字要成張重生。用圖層就改文字唔使重生。

具體接邊隻圖像 API（GPT Image、Gemini、其他），要按你實際攞到嘅帳戶同地區決定 ——
**價錢同可用性我唔會憑記憶報數，落單前去官方定價頁核。**
工作台呢邊唔綁死任何一家：`config/tools.md` 寫嘅係**工具類型**唔係品牌名，
換供應商唔使改工作台。

## 五、其他要接嘅嘢

| 功能 | 建議做法 | 成本重點 |
|---|---|---|
| **爬社交內容** | 官方 API 行得通就用官方（IG Graph API 要 Business 帳號＋審核）。小紅書冇公開 API → 人手匯出＋`distill.py`。 | 第三方爬蟲服務按次收費，而且會斷。**寧願一次過人手匯出 30 條**，比長期養一個會壞嘅爬蟲平。 |
| **影片轉文字** | Whisper 類模型，本機跑得（開源版）。 | 本機跑 = 零邊際成本。量細唔值得接雲端 API。 |
| **排程發布** | Meta Graph API（IG／FB 官方，免費）。小紅書、Threads 冇官方排程 API → 人手發。 | 官方 API 免費。第三方排程工具（Buffer 類）係月費，**四平台入面兩個都唔支援，未必抵**。 |
| **表單／名單** | 現成表單工具 + webhook 入 `data/inbox/`。 | 唔好自己起 CRM。 |
| **Dashboard** | 已經內置，`python -m workbench serve`，零依賴。 | $0。 |

## 六、一個月實際會用幾多（粗略量級）

以**一個客、每週 12 篇、四個平台**計：

| 項目 | 一個月大約 | 慳法 |
|---|---|---|
| 重複讀品牌知識庫 | 最大一舊 | 快取後跌到約一成 |
| 爬取抽取 | 第二大 | Haiku |
| 平台改寫 | 量最大嘅生成 | Sonnet + Batch（再減一半）|
| 研究／文案／QA | 量細但用 Opus | 唔慳 |

**次序做齊（快取 → Batch → 分層）之後，同「全部用 Opus 唔開快取」比，
一般可以跌到一個零頭。** 但實際數字要用你自己嘅 `response.usage` 量，
唔好信任何人（包括我）報嘅預估 —— 唔同客嘅語料長度差好遠。

量法：每次 call 記低 `response.usage`（`input_tokens`、`cache_read_input_tokens`、
`output_tokens`），跑一個星期，就有真數。

---

## 七、開頭一個月唔好做嘅嘢

- **唔好開自動發布。** 工作台預設 `publish_mode: review-only`，
  而且語氣信心度未到「高」就開，`workbench doctor` 會攔你。
- **唔好為咗慳錢跳過 QA。**
- **唔好一次接齊所有 API。** 先接生成同快取，跑三個真 campaign，
  睇實際塞喺邊，先決定下一個接咩。接咗但用唔著嘅 API，係純成本。
