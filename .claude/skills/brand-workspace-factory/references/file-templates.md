## BIBLE.md

一頁。長過一頁就冇人讀，冇人讀就等於唔存在。

```markdown
# <品牌名> 品牌憲法

> 最後更新：<日期> · 語料信心度：<高/中/低>

## 一句話定位
<賣咩，賣俾邊個，解決咩>

## 受眾（具體到可以認得出）
- 年齡／人生階段：
- 處境：（幾時、喺邊、心情點）
- 佢自己點形容個問題：「<原話>」
- 佢唔買嘅理由：

## 語氣三行
1. 好似 <一個具體嘅人物關係>
2. 每篇都要 <一個必做動作>
3. 從來唔會 <一個必唔做>

## 紅線（違反即退回，唔需要討論）
- [ ] <由 archetype + modifier 生成>
- [ ] <每條要可以機械式檢查>

## 證據來源
只可引用 `brand/brain/04-approved-claims.md` 入面嘅嘢。
呢份檔案為空 = 呢一輪唔可以落任何數據或個案 Claim。

## 邊啲嘢一定要人批
- <由步驟 1 第 5 條問題嘅答案生成>
```

## AGENTS.md

每個角色一份。**六個欄位缺一不可** —— 少任何一個，agent 就會喺嗰個位自己發揮。

```markdown
# <角色名> Agent

## Role
你係 <品牌名> 嘅 <角色>。

## Goal
<今次要完成嘅唯一一件事。一句。>

## Inputs（只可以讀呢啲）
- brand/BIBLE.md
- brand/brain/<列明邊幾個櫃桶>
- <上游交嚟嘅檔案路徑>

## Rules
- <具體到可執行。「保持專業」係廢話。>
- <每個關鍵 Claim 要保留來源連結>
- <唔可以自行決定品牌立場／對外承諾>
- <先出 N 個選項再由人揀，唔好直接落決定>

## 交付成果
交 `<明確路徑/檔名.md>`，包含：
- <欄位一>
- <欄位二>

## 人手檢查點
<咩嘢一定要等人批准先可以去下一站>
```

**寫 Rules 嘅要訣：**每條規則問自己「呢條規則可唔可以被違反得好明顯？」如果答案係唔可以（因為佢太抽象），咁就唔係規則。

## SKILL.md

技能係一個資料夾，SKILL.md 係入面嘅說明書。

```markdown
# <技能名>

## 用途
<解決咩問題。一句。>

## 適用場景
- <幾時用呢個技能>
- <幾時唔應該用>

## 需要讀嘅資料
- `01_brand/` → 指去 brand/brain/（引用，唔好複製）
- `03_platform_rules/<platform>.md`

## 執行步驟（SOP）
1. 讀 Brief — 確認目標、受眾、CTA、交付格式
2. 撮要用哋檔 — 由指定資料夾攞資料，唔好自己估
3. 睇平台規格 — 確認字數、節奏、格式限制
4. 叫工具處理 — <邊一步用邊類工具>
5. 檢查再交 — 跑 `04_qa/qa-checklist.md`

## 範例
**Input：**<真實嘅輸入樣本>
**Output：**<真實嘅輸出樣本>

## 常見問題
| 情況 | 原因 | 處理 |
|---|---|---|

## 注意事項
- <邊啲位最易出錯>
```

## MEMORY.md

工作台會唔會變好，全靠呢份檔案有冇人寫。

```markdown
# 決策與學習記錄

> 每次 review 之後補一條。唔好只儲存最後版本 —— 「點解改」比「改成點」有用。

## 已批准（可以再用）
| 日期 | 咩嘢 | 點解 work | 連結 |
|---|---|---|---|

## 已退回（唔好再犯）
| 日期 | 咩嘢 | 點解唔得 | 已補去邊層 |
|---|---|---|---|

## 已知問題
- <重複出現嘅錯，同對應嘅檢查項>

## 下次提醒
- <落一輪開工前要記得嘅嘢>
```

**「已補去邊層」呢欄係精髓。**填唔到嗰欄，即係你今次只係執咗份稿，冇改到系統 —— 下次會再犯。

## CHECKLIST.md

```markdown
# 交付前驗收

## 來源與證據
- [ ] 每個數據／個案 Claim 有 Source Receipt
- [ ] 冇引用 04-approved-claims.md 以外嘅證據
- [ ] 冇把同行觀點當成品牌立場

## 品牌
- [ ] 語氣對照 voice-profile.md：句長、開場、標點、稱呼
- [ ] 冇用禁用詞
- [ ] 平台規格符合 03_platform_rules/

## 紅線
- [ ] <逐條由 BIBLE 嘅紅線清單複製過嚟>

## 對外一致性
- [ ] 內容、landing page、表單、email 講緊同一件事
- [ ] CTA 清楚，下一步做咩冇歧義
- [ ] 連結行得通

## 交付完整性
- [ ] 交付物齊全（文字／圖／caption／CTA／來源）
- [ ] 檔名同路徑符合規範
```

## 八個櫃桶

`brand/brain/` 下面，檔名固定（agent 靠檔名搵嘢）：

| 檔名 | 放咩 | 幾時會空 |
|---|---|---|
| `01-positioning.md` | 使命、產品、價值、競爭位置 | 唔應該空 |
| `02-voice-profile.md` | 語氣（見 ingestion.md 嘅具體度要求） | 冇語料時標「未建立」 |
| `03-audience-language.md` | 受眾原話、反對理由 | 冇留言資料時會空 |
| `04-approved-claims.md` | 已批准嘅數據、個案、產品事實 | **第一版通常係空 —— 咁就寫「空」** |
| `05-hook-library.md` | 有效開場、成功例子（附連結） | 語料少時會薄 |
| `06-platform-rules.md` | 各平台格式、節奏、禁忌 | 唔應該空 |
| `07-review-log.md` | 批准／退回記錄 | 第一版一定空 |
| `08-learning.md` | 學到嘅有效做法、SOP 修訂 | 第一版一定空 |

**空櫃桶要明寫「（空）」同點解空**，唔好留白。留白嘅話 agent 唔知係「冇資料」定「未讀到」，會自己補 —— 而佢補嘅嘢就係幻覺嘅來源。

寫法：
```markdown
# 04 · 已批准主張／證據

（空）

第一版未有已授權嘅個案或數據。
**在此檔案為空期間，任何內容唔可以引用數字、研究、或客戶個案。**
補充方式：客戶提供書面同意嘅個案後，由人手加入並標明授權範圍。
```

## 同意登記（敏感個案客戶）

**幾時要：**客戶會用真實客人嘅相、身體、健康狀況或個人故事做內容。
典型係 `health-adjacent`、`beauty-efficacy`、`minors` 呢幾個 modifier。

呢類客戶嘅 `04-approved-claims.md` 要拆成兩條路 —— 撈埋處理係最常見嘅錯：

```markdown
### A · 品牌自身證據（低敏感）
認證、資歷、服務內容、價格。有官方文件核對完就可以入庫。

| 主張 | 證據 | 有效期 | 狀態 |
|---|---|---|---|

### B · 客戶個案／效果圖（高敏感）
每個案例要有一筆同意登記，冇登記就當唔存在。
```

同時建立 `data/consent/`，一個案例一個檔（**用編號，唔用姓名**）：

```
案例編號：
同意書：      <檔案位置>   ← 書面，唔係口頭
同意日期：
授權範圍：    □ 社交平台  □ 網站  □ 廣告  □ 印刷
授權期限：
可否露面：    <由品牌方定，通常係否>
取景範圍：    <由 style/brand-visual.md 嘅身體規範帶入>
撤回方式：    <點樣通知、幾耐內落架>
```

**三條規則寫入資料夾嘅 README：**

1. **Agent 唔可以寫入 `data/consent/`。**同意係法律事實，唔係可以推斷出嚟嘅嘢 ——
   agent 判斷「呢張應該冇問題」正正就係最危險嗰種錯。
2. **同意書正本唔好放喺 workspace。**放安全儲存，登記只記路徑。
3. **要有使用索引。**同意可以撤回，而撤回要做得到 —— 邊張相用咗喺邊個平台邊個帖。
   冇索引就撤唔到，因為你搵唔返張相出咗幾多個地方。第三條最多人漏。

### 紙本 legacy 同意

好多客戶做咗幾年，舊個案全部係紙本同意、冇電子版。**紙本係有效同意** ——
登記要嘅唔係電子簽名，係一個指得到嗰份文件嘅記錄。

但**唔好一刀切批准**。舊同意嘅問題通常唔係「有冇」，係「**範圍**」：
當年寫「同意用於本店宣傳」，而客戶今日要出小紅書同落廣告 ——
呢啲喺當時嘅同意書入面根本冇提過。

按**原文寫低嘅授權範圍**分三層：

| 層 | 原文寫咩 | 可以點用 |
|---|---|---|
| 🟢 A | 明寫包括社交平台／網上宣傳／廣告，或「不限媒介」 | 照用 |
| 🟡 B | 只寫「本店宣傳」「作品集」，或者冇寫用途 | 只可用喺原用途；出新平台要補充同意 |
| 🔴 C | 搵唔返紙本（記憶中講過、口頭答應） | **當唔存在** |

C 層咁嚴唔係因為保守，係因為**你證明唔到**。

**批量處理：**掃描 → 逐份睇授權範圍嗰段判層 → 開登記檔指去掃描件 →
B 層開一張名單統一補充。第二步唔可以跳；就算得二十份，逐份睇嗰一段
都係二十分鐘嘅事，而分錯層冇得補救。

**B 轉 A 唔使重簽。**一條訊息講清楚新平台同呈現方式，回覆截圖存低就係
電子補充同意，登記標 `A (supplemented)`。

登記模板要多兩欄：`tier`、`原文授權範圍`（**照抄，唔好意譯** ——
意譯嗰一刻你已經喺做判斷，而三個月後冇人記得原文寫咩）。

> 呢節講嘅係**記錄制度嘅設計**，唔係法律建議。分層同措辭如果涉及
> 重大商業決定，客戶應該諮詢法律意見。工作台嘅責任係令證據搵得返。

### 未處理原檔（raw）點擺

客戶交嚟嘅原檔通常**仲未過裁切規範** —— 可能有樣、可能超出取景範圍、
可能有可識別背景（屋企、衣物、紋身）。

**一張都唔好入 workspace。**

唔係因為 agent 會故意用，而係因為**佢分唔出邊張已處理、邊張未處理**。
放一張入去，就係製造一個等緊發生嘅洩漏。

界線畫喺：**只有已裁切、已對準、已登記同意嘅圖，先可以有路徑出現喺 workspace**
（而且係路徑，唔係複製品）。

三段式，全部喺外部儲存：

```
<外部儲存>/<client>/
├── 01_raw/_inbox/      啱啱收到，未配對案例編號
├── 01_raw/<case-id>/   已配對，未處理
├── 02_processed/       已裁切 ＋ 已對準
└── 03_consent/         同意書掃描
```

原始相片改名用 `scripts/case_rename.py`：`<case>_<stage>_<seq>_<date>.<ext>`，
例如 `SS001_d01_01_2026-08-20.jpg`。配對 before/after = 同 case、同 seq、唔同 stage。
**用編號唔用姓名** —— 姓名唔應該出現喺檔名。改名會寫低 `_rename-log.csv`
（原檔名 → 新檔名），係還原同追溯嘅憑證。

檔名做索引好過另開一份 CSV：CSV 要人手維護，改咗檔名或者搬咗位就錯咗而冇人知；
檔名跟住檔案走。

workspace 只放一份**追蹤表**（`data/consent/_PROCESSING.md`），記狀態唔記圖：
案例編號 · 收到日期 · raw 位置 · 已裁切 ⬜ · 已對準 ⬜ · 同意 tier · 可用 ⬜。
四格全部剔晒先算可用。

### 前後對比嘅「對準」係誠信問題，唔係美觀問題

姿勢、角度、光線、距離唔一致嘅前後對比會**誇大效果** —— 直接踩
`beauty-efficacy` 紅線。要對齊五樣：距離、角度、光線、姿勢
（**唔好一張收腹一張放鬆**）、後製（兩張同樣處理，唔用瘦身濾鏡）。

**做唔到對齊 → 唔好出對比圖。** 出單張或文字分享都可以，
但唔可以擺兩張唔可比嘅相埋一齊叫人自己比較。

### 素材來源嘅分工

呢個分別好易搞錯，但影響好大：

| 用途 | 應該用咩 | 唔好用咩 |
|---|---|---|
| 學品牌畫風 | **已出街嘅貼文圖** | 原始效果圖 |
| 做前後對比內容 | 有同意登記嘅個案 | 任何未登記嘅相 |

已出街嘅圖已經過咗品牌自己嘅裁切同同意標準，用嚟掃畫風冇新增風險；
而且嗰啲先係**受眾實際見到嘅嘢** —— 原始素材同最終呈現往往差好遠。
